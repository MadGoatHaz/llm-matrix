## 0. What This Document Is

This plan transforms `https://madgoathaz.github.io/llm-matrix/` from a **single-page data table** into a **complete multi-page educational resource** for running local LLMs. It is the architectural blueprint for the build.

The current site is one file: `index.html` (repo root), generated by `tools/generate.py` from `data/submissions.json`. It renders a filterable/sortable table of community submissions. That table is the *data* half of the product. This plan adds the *knowledge* half: a set of navigable guide pages, a community showcase, a comparison tool, and a proper landing page — all wrapped in a shared design system.

**The one-liner after this work:**
> "The place where you learn *what* to run, *why* it works that way, and *see* what real people are running on real silicon."

The forum thread (`https://forum.level1techs.com/t/256443`) is where the conversation happens. The website is where the reference lives. They are complementary, not competing — and the plan makes that division of labor explicit (Section 10).

## 1. Vision

### 1.1 The Shift

| | Before (now) | After (target) |
|---|---|---|
| **Shape** | One page, one table | Many pages, structured IA |
| **Job** | Show the data | Teach the concepts *and* show the data |
| **Entry point** | The table | A landing page with multiple doors in |
| **Reader model** | "Find my GPU row" | "Understand my options, then find my GPU row" |
| **Content source** | `submissions.json` only | `submissions.json` **plus** authored markdown guides |
| **Feel** | A spreadsheet | "The best docs site you've ever read, meets a spec sheet you actually want to use" |

### 1.2 Two Audiences, One Site

The site serves two jobs that a table alone can't:

1. **The Decider** — "I have a 4090 and 128GB RAM. What should I run for coding?" They want: the Matrix (filter to their tier/hardware), the use-case finder, the compare tool, and a backend guide. They skim.
2. **The Learner** — "Why is my 125B model only using 3B of it? What's a quant? What's eating my VRAM?" They want: the guides. They read.

A good site serves both without forcing one to scroll past the other. That's why it's multi-page with clear navigation, not one long scroll.

### 1.3 Non-Goals (carried over, still true)

- No user accounts, no login, no server-side state.
- No real-time updates — weekly rollup is the cadence.
- No Node.js, no JS framework, no build step (see Section 5).
- No paid hosting — GitHub Pages only.

## 2. Guiding Principles

### 2.1 Content Principles

Every concept in every guide follows a fixed 4-part shape:

> **What it is** (1 sentence) → **Why it matters** (1 sentence) → **How it works** (2–3 sentences) → **When to care about it** (practical, setup-specific guidance)

Additional rules:
- **Explain to a smart beginner.** Assume they know what a GPU, RAM, and a terminal are. Do *not* assume they know what "W4A16" or "KV cache" or "MoE" means.
- **Always close the loop on "your setup."** Every guide ends with a concrete "what does this mean for you" — tied to a tier, a use case, or a hardware choice.
- **Use analogies** where they clarify (e.g., "MoE is like a hospital with 100 specialists where only 3 see each patient").
- **Show real numbers** — VRAM formulas, token/s, power draw. No hand-waving.
- **Credit the community.** Where a concept is illustrated by a real submission, name the contributor. Make people feel seen (this is a core value of the project — see the existing "Respect the contributors" copy in `index.html`).
- **Flag uncertainty.** Where a topic is moving fast (NVFP4, Strata, MTP), say so explicitly instead of presenting it as settled.

### 2.2 Design Direction

- **Dark mode by default** (tech audience; extend the existing palette in `index.html`).
- **Clean, modern, not corporate.** No stock photos, no gradients-into-the-sunset, no "trust us, we're a company."
- **Cards, not walls of text.** Chunky content into scannable cards with a headline + 1–2 lines + an expand.
- **Visual diagrams in pure CSS** — no images. KV-cache growth, tensor-parallel splitting, MoE expert routing, the offload stack (VRAM→RAM→SSD) all drawn with CSS boxes/arrows.
- **Progressive disclosure.** Simple answer first (a one-line card or `<details>`), full explanation on expand. The reader controls depth.
- **Mobile-first responsive.** Build the narrow layout, then widen. Touch targets ≥ 44px.

### 2.3 Voice

- Second person, direct: "your GPU," "your VRAM," "you'll want."
- Plain words over jargon; when a term is introduced, define it in place.
- Confident but honest: "this is the fastest path" not "this is the *best* path in all possible worlds."
- A little personality is welcome (the project already uses emoji in headers), but never at the expense of clarity.

### 4.4 Guide: Quantization — `/guides/quantization/`

**Purpose:** Demystify the single most common source of confusion: "what is a quant, and which one do I pick?"

**Layout (each concept follows the 4-part shape):**
1. **Header + "The 30-second version"** — one card: "A quant is a way to store model weights using fewer bits, so a big model fits in less VRAM. You trade a little quality for a lot of memory. The name (W4A16, FP8, Q4_K_M) tells you *how* it was compressed."
2. **What quantization is** — the core definition + a CSS diagram showing FP16 (2 bytes) → INT4 (0.5 bytes) per weight, with a "fits 4× more model" callout.
3. **The naming code** — a table decoding the common suffixes:
   - **W4A16** = 4-bit *Weights*, 16-bit *Activations* (the weights are tiny, the math runs at full precision).
   - **W8A8** = 8-bit weights *and* 8-bit activations.
   - **Q4_K_M / Q5_K_M / Q6_K / Q8_0** = GGUF "K-quant" family (M = medium granularity; the K = "key/value" block format).
   - **FP8 / BF16 / FP16** = floating-point precisions.
   - **NVFP4 / MXFP4** = the new 4-bit microscaling formats (flag: actively evolving).
4. **The precision ladder** — a CSS staircase from FP32 → FP16/BF16 → FP8/INT8 → INT4, with a "quality vs. size" note at each step and "which tier of GPU this is for."
5. **Symmetric vs. asymmetric, and group sizes (G128/G64)** — short cards explaining the two ideas in one breath.
6. **The VRAM formula** — the single most useful thing on the page: `VRAM ≈ (params × bytes_per_weight) ÷ 1024³ + KV + overhead`. Work one concrete example end-to-end (e.g., 27B model, Q4_K_M ≈ 0.55 bytes/param ≈ ~15GB + KV). Tie to a Matrix tier.
7. **"Which quant should I pick?"** — a decision card set:
   - Tight on VRAM, want max quality-per-byte → the K-quants (Q4_K_M is the sweet spot).
   - NVIDIA + vLLM, want speed → FP8.
   - Brand-new 4-bit on hardware that supports it → NVFP4/MXFP4 (flag: new, check backend support).
   - "Just wants it to work" → Q4_K_M / Q5_K_M.
8. **Tie-back** — "This is why the Matrix has a Quant column: it tells you how much VRAM a model really needs."
9. **Related** → File Formats, Quantization Methods.
10. **Footer.**

**Data dependencies:** mostly static; the VRAM formula example can reference a real Matrix submission.

### 4.5 Guide: File Formats — `/guides/file-formats/`

**Purpose:** "GGUF vs safetensors vs MLX — what's inside, and which do I download?"

**Layout:**
1. **30-second version** — "The model's weights are stored in a file format. The format determines which software can read it. Pick the format your backend wants."
2. **Three format cards** (one per format), each with: what it is, what's inside (weights + metadata + tokenizer for GGUF; sharded tensors for safetensors; Apple-native layout for MLX), who makes it, and its key trait.
   - **GGUF** — single self-contained file; the llama.cpp world; portable; great for AMD/CPU/mixed; limitation: historically no native FP8.
   - **Safetensors** — the PyTorch/vLLM standard; multi-file "shards" (why a 70B model is 8 files); the format for training + production servers.
   - **MLX** — Apple Silicon native; uses unified memory; what makes it different.
3. **"Which do I download?"** — a decision table:
   | You use… | Download… |
   |---|---|
   | llama.cpp / Ollama / LM Studio / Unsloth (GGUF mode) | GGUF |
   | vLLM / TensorRT-LLM / Strata | safetensors (often FP8) |
   | MLX (Apple) | MLX |
4. **The "shards" explainer** — why a big model is split into `model-00001-of-00008.safetensors` etc., and why it doesn't matter to you (the backend reassembles).
5. **Size estimation** — reuse the VRAM formula from the Quantization guide (cross-link), with a worked example showing the same model in GGUF-Q4 vs safetensors-FP8 vs MLX and the size difference.
6. **Tie-back** — the Matrix's Model column often names the format implicitly (e.g., `…-GGUF`).
7. **Related** → Quantization, Backends.
8. **Footer.**

### 4.6 Guide: Quantization Methods — `/guides/quantization-methods/`

**Purpose:** "How is the quant *made*? Why does one 4-bit quant beat another?"

**Layout:**
1. **30-second version** — "Two 4-bit files can be very different quality. The difference is *how the rounding was done*. The method matters more than the bit count."
2. **The methods, each as a card** (4-part shape + a "quality rank" + "which backends" + "when to use"):
   - **RTN (Round-To-Nearest)** — the baseline; just round each weight. Fast to make, lowest quality. What "naive quant" means.
   - **GPTQ** — Hessian-based; corrects each weight's rounding error against the ones already set. Better than RTN; the classic pre-vLLM 4-bit.
   - **AWQ (Activation-Aware Quantization)** — protects the weights that matter most (the "salient" ones the activations hit hard). Often beats GPTQ at the same bit width; cheap to produce.
   - **AutoRound** — gradient-optimized rounding; finds near-optimal round-up/round-down per weight. Popular for W4A16; strong quality at 4-bit; this is the one behind many vLLM W4A16 releases.
   - **SmoothQuant** — a different trick: mathematically moves quantization difficulty *from activations to weights* so both can be 8-bit. This is what makes W8A8 practical.
3. **The GGUF K-quant family** — a sub-section: Q4_K_M, Q5_K_M, Q6_K, Q8_0, IQ3_S, IQ4_XS, I-Nano, UD-Q2_K_XL — what the letters mean, and the **quality hierarchy** (a CSS ladder: Q8_0 > Q6_K > Q5_K_M > Q4_K_M > IQ4_XS > IQ3_S > I-Nano/UD-Q2, with a "quality per byte" note that the smart low-bits like I-Nano can punch above their weight).
4. **NVFP4 / MXFP4** — the new microscaling formats; how they differ from plain INT4 (per-group scaling factors), what hardware supports them, why they're called "the golden ticket" for 4-bit — and an explicit **flag: new and moving fast; verify backend support before betting on it.**
5. **Comparison table** — rows = methods; columns = quality impact, speed impact, VRAM savings, backends that support it, best use. This is the "spec sheet you actually want to use."
6. **Tie-back** — "When you see 'W4A16-AutoRound' in the Matrix Quant column, now you know that's a 4-bit weight / 16-bit activation quant made with gradient-optimized rounding."
7. **Related** → Quantization, File Formats, Backends.
8. **Footer.**

### 4.7 Guide: Model Architectures — `/guides/model-architectures/`

**Purpose:** "Dense vs MoE vs Hybrid. What does 'A3B' mean? What's MTP?"

**Layout:**
1. **30-second version** — "Not all '35B' models are equal. Some use all 35B of their brain for every word; some only turn on a small part. That difference is the whole story of why a 125B model can run at 200 tok/s on a consumer box."
2. **Dense** — every parameter active on every token. Examples from the Matrix (Qwen3.8-27B, DeepSeek-V4-Pro). The cost: VRAM scales with *total* params.
3. **MoE (Mixture of Experts)** — the model has many "expert" sub-networks; a router activates only a few per token.
   - **CSS diagram:** a token flowing in, a router fan-out to a small set of lit "expert" boxes, the rest dimmed.
   - **"A3B" decoded** — 3B *active* parameters out of ~35B *total*. The "A" = active.
   - **Why it matters for local** — 125B total but 3B active → the *compute* per token is tiny (fast) even though the *weights* are huge (need the VRAM/RAM to hold them). This is the crux.
4. **Hybrid** — architectures mixing dense and MoE layers; when you'll see them.
5. **MTP (Multi-Token Prediction)** — a head that predicts several future tokens at once; how it enables **speculative decoding** (the draft-then-verify pattern). Which current models ship it (e.g., the `…-MTP` entries in the Matrix, Gemma-4 `a4b-it-mtp`).
6. **Speculative decoding** — a CSS diagram of the draft→verify loop; how MTP and n-gram tables turn "1 token at a time" into "several at a time" for a big decode-speed boost.
7. **Reading the Matrix** — how to spot arch + active params in a model name, and what it predicts about speed vs. memory.
8. **Related** → KV Cache (MoE + long context = memory math), Backends.
9. **Footer.**

### 4.8 Guide: KV Cache — `/guides/kv-cache/`

**Purpose:** "The silent memory eater. Why does my context keep growing VRAM, and should I quantize it?"

**Layout:**
1. **30-second version** — "For every token you've processed, the model stores a small memory of the attention keys and values. That storage is the KV cache — and it grows with your context, independent of the model's weights."
2. **What it is** — the definition; why it's separate from weights (weights are fixed; KV is per-conversation and grows).
3. **Why it grows linearly** — a CSS bar chart: KV size vs. context length (4k → 32k → 128k → 256k), showing the linear climb.
4. **The formula** — `KV ≈ layers × heads × head_dim × seq_len × 2 × bytes_per_element`. Work a concrete example and show how a 27B model's KV at 256k can rival the weights in size. This is the "why my 16GB card chokes at 64k" answer.
5. **KV quantization** — FP8 / INT8 / INT4 KV. What you save, what you risk.
6. **When to quantize KV** — creative writing, casual chat, VRAM-constrained, long context where you can't afford FP16 KV.
7. **When NOT to quantize KV** — coding, RAG, math, long-context precision work (agentic coding that must not lose the thread). The Matrix's KV column tells you what each setup chose — cross-link it.
8. **PagedAttention** — vLLM's technique for managing KV memory in pages (no fragmentation, efficient batching). One card.
9. **Prompt caching** — how reusing a cached prefix (e.g., a system prompt) gets a ~90% hit rate and why that matters for agents. One card, tied to Strata.
10. **Tie-back** — "This is the KV column in the Matrix: 'quantized KV' vs 'FP16' tells you how much headroom a setup left for long context."

### 4.9 Guide: Context Extension — `/guides/context-extension/`

**Purpose:** "The model says 32k. Can I run 128k? What breaks, and how?"

### 4.10 Guide: Backends — `/guides/backends/`

**Purpose:** The deep dive on every inference engine. "When do I use vLLM vs llama.cpp vs Strata vs MLX?"

**Layout:**
1. **30-second version** — "A backend is the program that loads the model file and runs it on your hardware. Same model, different backend = different speed, features, and ease. Pick the one that fits your hardware and your use case."
2. **The master comparison table** (the spec sheet): rows = the 11 backends; columns = Formats · GPU/OS · Key strength · Best for · Avoid when. This is the single most-referenced table on the site.
3. **One card per backend** (4-part shape + "when to choose / when not to"):
   - **llama.cpp** — the universal baseline; GGUF; runs on CPU+GPU+AMD+Apple; the reference point.
   - **llama-swap** — multi-model auto-swapping on a single GPU; OpenAI-compatible API.
   - **Ollama** — "Docker for LLMs"; easiest start; GGUF; limited features.
   - **LM Studio** — GUI wrapper over llama.cpp; model browser; great first step.

   - **Strata** — the hybrid offload engine; 125B+ on consumer hardware across VRAM+RAM+SSD. *(flag: beta/evolving)*

4. **"Pick your backend" flow** — a decision tree (CSS):

   - NVIDIA, casual? → Ollama / LM Studio / Unsloth.
   - NVIDIA, production / multi-user / big context? → vLLM.

### 4.11 Guide: Multi-GPU — `/guides/multi-gpu/`

**Purpose:** "I have two (or four, or eight) GPUs. How do I split a model across them?"

**Layout:**
1. **30-second version** — "One card too small for the model? Split the model across cards. There are three ways to split it, and the way you split it changes speed."
2. **The three split strategies** (each a card + a CSS diagram):
   - **Tensor parallel** — split each layer's matrices across cards; cards work *together* on every token; fastest, needs fast interconnect; what vLLM does.
   - **Pipeline parallel** — split by *stages* (layer 1–20 on card A, 21–40 on card B); cards work *in sequence*; simpler, more inter-card latency.

3. **The interconnect matters** — NVLink (NVIDIA) vs PCIe; AMD XGMI / Infinity Fabric; why a slow bus tanks tensor-parallel speed. A small CSS "bus width" diagram.
4. **Practical setups** — a table:

   - 4× 24GB (96GB) → what fits.
   - 8× 24GB (192GB) → the big-model territory.

5. **When multi-GPU is worth it** vs "just buy one bigger card" — the honest tradeoff (cost, power, complexity).

### 5.3 The Generator (`tools/generate.py`) — how it works

`generate.py` becomes the single entry point that renders **all 15 pages** in one run. Its responsibilities:

1. **Load inputs** — `data/submissions.json`, `tools/schema.json`, `tools/tags.json`, and every `content/**/*.md`.
2. **Build the page shell** — a `template.py` that takes `(title, body_html, page_id, active_nav)` and returns a complete `<!DOCTYPE html>…</html>` with:
   - `<head>`: the shared `<link rel="stylesheet" href="../assets/css/site.css">` (depth-adjusted relative path), meta/OG tags, `<body data-page="…">`.
   - The shared **top nav** (with the Guides dropdown) and **footer** (attribution + forum CTA + not-official line).
   - The page's `<main>` body.
3. **Render content pages** (guides, about) — for each `content/**/*.md`, run the markdown → HTML converter (5.4), inject into the shell, write to the mapped path (`content/guides/kv-cache.md` → `guides/kv-cache/index.html`).
4. **Render data pages** (matrix, community, compare) — `data_pages.py` builds the tables/cards from `submissions.json` (reusing the existing row/filter/sort logic already in `generate.py`), injects into the shell, writes output.
5. **Render the homepage** — assembles the hero, quick-GPU-lookup, use-case finder, community highlights, and guides grid (mix of static fragments + live data), writes `index.html`.
6. **Write `data.json`** — the full submissions payload at the root (already done today) so any page can fetch it if needed.
7. **Report** — a summary line per page written (so a broken page is obvious in the log).

**Idempotency & safety:** the generator overwrites only the paths it owns (all the `*/index.html` it maps + root `index.html` + `data.json`). It never touches `assets/`, `content/`, or `tools/` — those are the hand-authored inputs. A page that fails to render is reported, not silently skipped.

**Relative-asset paths:** because pages live at different depths (`/` vs `/guides/kv-cache/`), the shell computes the correct relative prefix to `assets/` (`./`, `../`, `../../`). This is the one fiddly detail — handled once in `template.py`.

### 5.4 Markdown → HTML (no framework)

- Use the **`markdown`** Python package (PyPI) with the `tables`, `fenced_code`, `toc`, and `sane_lists` extensions. This is *not* a JS framework and *not* a build step — it's a pure-Python library invoked inside `generate.py`, exactly in the spirit of the existing dependency-free pipeline. (Requirement: `pip install markdown` in the build environment / GitHub Action.)
- **Fallback if zero external deps is a hard requirement:** a minimal converter in `tools/site/markdown.py` supporting exactly the constructs we use (headings, paragraphs, lists, tables, fenced code, bold/italic, links, and pass-through `<details>/<summary>`/custom divs for CSS diagrams). Recommended to start with the `markdown` package for robustness; the minimal converter is the contingency.
- **Front-matter:** each `content/**/*.md` starts with a small YAML/JSON block the generator reads for `title`, `description`, `nav` (which nav item is active), `related` (sibling guide links), and `icon`. The generator strips this from the body and uses it to build the shell + Related links.
- **CSS diagrams in markdown:** authored as raw HTML `<div class="diagram …">…</div>` blocks inside the markdown (the `markdown` package passes raw HTML through). This is how we get "visual diagrams, no images" — pure CSS classes defined in `site.css`.

### 5.5 Shared CSS (`assets/css/site.css`)

One stylesheet, organized in layers:
1. **Tokens** — the existing `:root` palette (`--bg`, `--surface`, `--border`, `--text`, `--text-muted`, `--accent`, `--highlight`, `--green`, `--red`), **extended** with a few more: `--accent-2` (for AMD/NVIDIA distinction), `--radius`, spacing scale, and a shadow scale. Dark is the default; a `:root.light` override is optional (the old plan mentioned a toggle — keep it simple: dark-only for v1, toggle is a Phase 4 nicety).
2. **Reset + base** — the existing `*`/`body` rules.
3. **Layout** — `.container`, the sticky `.topnav`, `.footer`, and the responsive grid helpers.
4. **Components** — the reusable pieces, each a self-contained class family:
   - `.card` / `.card-grid` (the workhorse; homepage, guides index, community).
   - `.btn` / `.btn-primary` / `.btn-forum` (reuse existing).
   - `.stat` / `.stats` (reuse existing).
   - `.chip` (use-case finder, filter tags).
   - `.table` + `.tier-header` + `.highlight` + `.hide-mobile` (reuse/extend the existing dashboard table styles).
   - `.detail-panel` (the Matrix row→detail slide-in).
   - `.nav-dropdown` (the Guides nav menu).
   - `.callout` (the "30-second version" boxes, the "flag: new/uncertain" boxes — a colored left-border card).
   - `.diagram` + diagram sub-classes (`.diagram--kv`, `.diagram--moe`, `.diagram--offload`, `.diagram--tensor`, `.diagram--pipeline`, `.diagram--bus`, `.diagram--ladder`) — all CSS-drawn, no images.
   - `.progressive` (styles the `<details>/<summary>` pattern consistently across all guides).
5. **Responsive** — mobile-first: base styles are the narrow layout; `@media (min-width: 768px)` and `@media (min-width: 1024px)` widen. The existing `@media (max-width: 768px)` table-collapse logic is carried forward.

### 5.6 Shared JS (`assets/js/site.js`)

Vanilla JS, one file, no deps. Responsibilities:
1. **Nav** — active-item highlighting from `<body data-page>`; mobile hamburger toggle; Guides dropdown open/close.
2. **Filtering** — a generic `initFilter(containerId, {search, selects})` that powers **three** pages (Matrix, Community, Compare-picker) by reading `data-*` attributes and hiding non-matches. Reuses the existing `applyFilters` logic, generalized.
3. **URL sync** — on filter change, write state to the query string (`history.replaceState`); on load, read the query string and restore filters/selection. This is what makes Matrix/Community/Compare **shareable**.
4. **Sorting** — the existing `sortTable` (numeric-aware, within-group), generalized to any `.table`.
5. **Detail panel** — open/populate/close the Matrix row→detail panel from the row's data.
6. **Compare selection** — checkbox tracking; build the `/compare/?a=&b=` deep link; on the Compare page, read the selection and render the diff-highlighted table.
7. **Progressive disclosure** — a tiny enhancer for `<details>` (optional: persist open state, animate). The native `<details>` works without JS, so this is a nicety, not a dependency.
8. **Copy-to-clipboard** — for "Copy launch command" buttons.

**Launch-command derivation (5.5 note):** a small map in `site.js` (or precomputed by the generator) turns a submission's `backend` + `model` + `quant` into a representative command string (e.g., `llama-server -m model.gguf -ngl 99`, `vllm serve model --tensor-parallel-size 2`, `strata …`). It's a *helper suggestion*, clearly labeled "example command" — not a guarantee — and it makes the tool feel concrete.

- **Location:** `content/**/*.md`. One file per page (guides + about). The generator maps path → URL.
- **Front-matter (top of each file):**

  title: KV Cache
  description: The silent memory eater — why context grows your VRAM.

  icon: 🧠
  related: [context-extension, hybrid-offload, model-architectures]

- **Body structure:** lead with the "30-second version" callout, then the 4-part concept cards, then a comparison table where useful, then CSS diagram(s), then the "Tie-back to your setup" close, then "Related" (auto-built from front-matter).
- **Diagrams:** authored as raw HTML `<div class="diagram diagram--kv">…</div>`; all styling lives in `site.css`. No images, no SVG files — pure CSS boxes and borders.
- **Tone & length:** a guide is 600–1,200 words of *authored* prose plus its tables/diagrams. Skimmable, not a textbook.
- **Accuracy gate:** every number in a guide must come from the research output or a real Matrix submission. If the research flags something as uncertain, the guide says so.

| **Prerequisite** | Requires Discourse to read | Universal — any browser, no account |
| **Role** | **Where the conversation happens** | **Where the reference lives** |

They are **complements, not competitors.** The forum is the living, debating, updating source. The website is the distilled, navigable, teachable destination. The site links back to the forum for discussion and submission; the forum links to the site for the structured view. A reader can start in either and flow to the other.
